收尾。

附加指令：$ARGUMENTS

先从对话历史中确定上下文。

上下文检测规则：
- 如果对话中已提到某个 GitHub issue 或 PR，使用该既有上下文。
- 如果工作来自 `/is` 或 `/pr`，假定 issue 或 PR 上下文已从对话和已完成的分析工作中得知。
- 如果对话历史中没有任何 GitHub issue 或 PR，将其视为非 GitHub 工作。

除非我在本次请求中明确覆盖某些内容，否则按顺序执行以下操作：

1. 按仓库的 changelog 规则，在相关包的 `## [Unreleased]` 下添加或更新 changelog 条目。
2. 如果本任务关联某个 GitHub issue 或 PR，且本会话尚未发布过最终的 issue/PR 评论，则以我的口吻起草、预览，并只发布这一条最终评论。评论必须以下面这行精确的独立免责声明结尾，不得有任何变体：

   ```text
   This comment is AI-generated by `/wr`
   ```
3. 只提交你在本次会话中修改的文件。
4. 如果本任务恰好关联一个 GitHub issue，在提交信息中包含 `closes #<issue>`。如果关联多个 issue，停下来询问用哪个。如果不关联任何 issue，提交信息中不要包含 `closes #` 或 `fixes #`。
5. 检查当前 git 分支。如果不是 `main`，停下来询问如何处理。除非我明确说明，否则不要从其他分支推送。
6. 推送当前分支。
7. 如果本任务恰好关联一个 GitHub issue，推送后明确以 `completed` 理由关闭该 issue，让 `.github/` 中的 issue 关闭工作流得以运行。这只适用于 issue，不适用于 PR。
   - 检查 `gh issue view <issue> --json state,stateReason,labels`。
   - 如果 issue 是打开的，运行 `gh issue close <issue> --reason completed`。
   - 如果 issue 已关闭但理由不是 `COMPLETED`，先重新打开，再用 `gh issue close <issue> --reason completed` 关闭，让 GitHub 产生一个新的关闭事件。
   - 如果 issue 已以 `COMPLETED` 关闭，保持关闭状态，除非 `inprogress` 标签还在；此时重新打开并以 `completed` 理由再次关闭。

约束：
- 绝不暂存无关文件。
- 绝不使用 `git add .` 或 `git add -A`。
- 代码有变更时，提交前运行必需的检查。
- 除非我明确要求，不要开 PR。
- 如果这不是 GitHub issue 或 PR 相关的工作，不要发布 GitHub 评论。
- 如果本会话已发布过最终的 issue/PR 评论，除非我明确要求，不要再发。
- 在 `main` 以外的分支上工作时，跳过 changelog。
