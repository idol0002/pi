# 安全地运行 Pi

把模型生成的命令和代码当作不可信内容。Pi 能以启动它的账户的权限读取、修改和执行文件，且不会在每次工具调用前请求批准。扩展、包安装器、语言服务器和其他子进程以同样的权限运行，除非有操作系统或虚拟化边界限制它们。

文件、注释、指令、命令输出和模型响应都可能通过提示词注入引导模型。项目信任控制启动时加载哪些项目资源，但不会让这些内容或由此产生的行为变得安全。

安全的来源是限制 Pi 在某个生成行为出错或怀有恶意时能访问和影响的文件、凭据、进程和网络服务。查看记录、使用项目信任、审查变更都不能构成安全边界。

## 选择运行方式

不同的运行方式对生成命令可访问的内容施加不同限制：

| Pi 的运行方式 | 受保护的内容 |
|---|---|
| 直接运行，拥有其操作系统用户的权限 | 该用户无法访问的一切。专用用户账户可以收窄这些权限，但 Pi 仍与其他用户共享操作系统和网络。 |
| 完全在容器、虚拟机或沙箱内 | 你未暴露给该环境的宿主文件和进程。如果你把凭据和网络服务放进环境，它们仍可被访问。这通常是实践上最强的选项。 |
| 在隔离环境之外运行，只有内置工具在环境内运行 | 宿主资源受到保护，免于通过这些工具执行的操作。Pi 自身和其他扩展仍在边界之外，因此这是一种较窄的隔离形式。 |

工作文件夹控制资源发现和工具的默认位置，但不能阻止命令访问 Pi 进程可用的其他路径。

无论选择哪种方式，只提供任务所需的文件和服务。尽量把凭据放在环境之外，或使用范围窄、寿命短的凭据。命令不需要网络时限制网络访问。

各隔离方式的设置说明和限制见[在隔离环境中运行 Pi](containerization.zh-CN.md)。

## 理解项目信任

项目信任控制 Pi 是否加载工作文件夹提供的大多数设置和资源。它防止文件夹在你批准之前静默加载可执行扩展。

项目信任不是完整的启动边界。Pi 在选择或创建会话时会读取项目 `sessionDir` 设置，这发生在解析项目信任之前。拒绝信任会阻止其余项目设置和受保护资源加载，但无法撤销那次初始的会话目录查找。

项目信任不限制工具调用能访问或影响什么。Pi 启动后，启用的工具仍使用 Pi 进程的操作系统权限。文件夹中的指令和其他内容也会影响模型。

### 受项目信任保护的资源

Pi 从当前工作目录发现以下任何资源时，都需要项目信任决定：

- `.pi/settings.json`
- `.pi/mcp.json`
- `.pi/extensions`、`.pi/skills`、`.pi/prompts` 或 `.pi/themes`
- `.pi/SYSTEM.md` 或 `.pi/APPEND_SYSTEM.md`
- 当前目录或祖先目录中的项目 `.agents/skills`

空的 `.pi` 目录不需要项目信任。

授予项目信任后，Pi 可以加载：

- 项目设置
- 来自 `.pi/mcp.json` 的项目 MCP 服务器
- `.pi` 下的扩展、技能、提示词模板、主题和系统提示词文件
- 项目设置中配置的缺失包
- 项目本地扩展和项目包扩展

拒绝项目信任会跳过这些受保护资源，但上文所述的初始 `sessionDir` 查找除外。

`AGENTS.override.md`、`AGENTS.md`、`CLAUDE.md` 等上下文文件无论项目信任如何都会加载，除非你禁用上下文加载。即使你拒绝了项目信任，也要把文件夹中的指令当作不可信输入。

### Pi 如何决定信任

命令行的 `--approve` 或 `--no-approve` 覆盖最先生效。存在受保护资源且没有命令行覆盖时：

1. 用户级和命令行扩展可以处理 `project_trust` 事件。第一个返回 yes 或 no 的扩展拥有该决定。
2. 没有扩展做决定时，Pi 查找当前目录或其父目录的已保存决定。取最近的那个。
3. 没有适用的已保存决定时，Pi 遵循全局 `defaultProjectTrust` 设置，默认值为 `"ask"`。

已保存的决定使用规范化的目录路径，存放在：

```text
~/.pi/agent/trust.json
```

用 `/trust` 为以后的 Pi 进程保存决定。

### 无交互提示时的项目信任

打印、JSON 和 RPC 模式无法显示内置信任提示。如果没有命令行覆盖、扩展决定或已保存决定适用：

- `defaultProjectTrust: "always"` 加载受保护的项目资源。
- `defaultProjectTrust: "ask"` 或 `"never"` 跳过它们。

自动化运行需要明确的一次性决定时，用 `--approve` 或 `--no-approve`。

## 降低影响并改善恢复

以下实践不能替代隔离，但能减少暴露或让恢复更容易：

- 只给 Pi 任务所需的文件和服务访问权。
- 大幅变更前使用快照、备份或版本控制。
- 加载扩展和包之前先审查。扩展在 Pi 进程内执行。
- 优先使用范围窄、寿命短的凭据。
- 把结果应用到其他系统之前，审查 diff 和生成输出。
- 导出或分享会话之前先审查。它们可能包含 prompt、工具参数、命令输出、文件内容以及对话中暴露的凭据。

## 报告安全问题

遵循仓库的[安全策略](https://github.com/earendil-works/pi/blob/main/SECURITY.md)。安全相关的报告不要开公开 issue。

预期的本地 agent 行为、来自不可信内容的提示词注入、缺少内置沙箱，以及用户安装的扩展或技能的行为，通常都在安全边界之外——除非报告能演示权限边界绕过，或本地用户原本不具备的访问能力。
