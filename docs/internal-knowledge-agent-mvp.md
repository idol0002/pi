# 企业知识库 Agent 首版实施清单

状态：已完成后端与权限、文档入库、关键词排序、可选向量混合检索、追问补全、通用 OpenAI 兼容问答接口及同源网页；支持 PDF／DOCX 解析、本地扫描件 OCR、页码引用、PDF 预览和正文复核。旧版 DOC 转换入口需要配置 LibreOffice。默认回答演示、向量关闭，无需密钥。生成和向量模型的配置位置已预留，由使用者自行填写；真实服务效果和试点验收仍待完成。

首版验收目标：管理员上传文档并授权，员工只能查询获授权的知识，回答可以定位原文。

## 第二阶段：文档入库与检索（已实现）

- 支持 Markdown／TXT（1 MiB）和 PDF／Word（20 MiB），原件和任务持久化在本地私有数据库中。
- PDF 逐页提取文字或通过本地 RapidOCR（PP-OCRv4 模型）识别图片；DOCX 提取正文、表格和内嵌图片，旧版 DOC 可通过配置的 LibreOffice 转换。
- 分块保留页面或正文块来源；PDF.js 同源预览支持页码定位和区域高亮。识别有疑点的版本先由维护者复核，可校对文字后原子发布。
- 后台按章节、段落和长度分块，保留版本、章节、行号和精确文本偏移，建立中英文关键词索引。
- 检索、版本原文、原件下载和片段读取均检查当前权限；只检索当前生效版本。
- 新版本成功后原子替换旧版本，失败时保留旧版本；提供任务查询、最多 3 次处理和手动重试。
- 删除立即阻止检索及来源访问，后台清理内容；重启恢复排队与中断任务，并继续删除清理。

当前为单进程开发实现。关键词排序、同源摘录去重、OpenAI 兼容向量接口、后台补建与权限过滤已实现；向量功能默认关闭，显式配置后启用。独立任务调度、近似向量索引和对象存储在部署阶段继续完善。

## 应用边界

- 员工问答页：选择获授权的知识库、提问、查看流式回答、打开引用原文、查看自己的会话。
- 管理后台：创建知识库、设置成员权限、上传文档、查看处理状态、更新和删除文档。
- 业务后端：身份认证、权限判断、文档管理、检索、会话管理、调用 Pi、向网页推送事件。
- 异步处理进程：解析文档、分块、调用向量模型、建立索引、重试失败任务。

公司应用通过公开接口使用 `pi-agent-core` 和 `pi-ai`。首版优先新增业务模块；只有公开接口无法满足具体需求时，再评估 Pi 核心改动。

当前网页采用 React 19、TypeScript 和 CSS，复用原有业务 API，由 Node 在启动时通过 esbuild 打包为同源页面资源，不增加独立的前端启动步骤。登录、会话、流式回答、文档管理和正文复核通过组件及 Hooks 管理。后端使用 TypeScript；开发阶段通过 PGlite 在本机持久化 PostgreSQL 数据。后续部署按独立 PostgreSQL 与 pgvector 设计，原文件接入私有对象存储。中文关键词检索已采用分词和相邻双字词，试点仍需用样本文档验证召回效果。

## 权限规则

首版按知识库给用户组授权，文档继承所在知识库的权限。先提供三种权限：

- 阅读：查询知识库、查看文档及引用原文。
- 维护：拥有阅读权限，可以上传、更新和删除文档。
- 管理：拥有维护权限，可以管理知识库及授权。

知识库的初始管理权限由可信的后台管理流程分配。默认不授权；前端提交的身份、用户组、权限值不能作为授权依据。

每次请求从已验证的登录信息获取员工身份，再由后端解析其用户组和权限。前端选择的知识库只能缩小查询范围。

- 关键词检索和向量检索都在查询中附加权限约束，返回给重排序服务和生成模型的片段必须已通过鉴权。
- 根据文档 ID 获取内容、预览原文、下载文件时，重新检查当前权限。
- 会话归创建员工所有；读取、续聊和取消生成都检查所属员工。
- 授权变更立即影响后续访问。即使索引清理尚未完成，查询也必须以当前权限和文档状态为准。
- 首版不启用跨员工共享的回答缓存。保留每条知识型回答的来源关联；撤权后，在展示历史或构建模型上下文前重新校验，屏蔽含无权来源的回答和证据。

## 最小数据结构

首版员工及用户组来自后端的测试身份适配器，后续替换为公司身份系统。当前迁移已实现身份、会话、知识库授权、文档与版本、关键词及向量索引、入库任务、消息及来源关联。开发阶段原件存入 `document_versions.source_bytes`，模型维度与配置标识保存在 `embedding_profiles`，片段向量保存在 `chunk_embeddings`。来源关联在文档正文清理后保留，供历史回答的权限和删除校验使用。

- `knowledge_bases`：知识库 ID、名称、状态、权限版本。
- `knowledge_base_grants`：知识库 ID、用户组 ID、授予的权限。
- `documents`：文档 ID、知识库 ID、标题、状态、当前生效版本。
- `document_versions`：版本 ID、文档 ID、原件存储位置、内容摘要、解析状态、上传人及时间。
- `document_chunks`：片段 ID、文档版本 ID、正文、页码或章节、向量及向量模型标识。
- `ingestion_jobs`：文档版本 ID、处理状态、重试次数、失败原因。
- `conversations`：会话 ID、员工 ID、选择的知识库、创建及更新时间。
- `messages`：会话 ID、消息角色、内容、完成状态、模型用量。
- `message_sources`：消息 ID、引用编号、文档 ID、版本 ID、片段 ID。

文档权限通过所属知识库实时判断。向量只对应指定的文档版本和向量模型；更换向量模型时需要重新建立对应索引。

## 入库流程

1. 检查上传者对目标知识库的维护权限，并校验允许的文件类型及大小。
2. 保存私有原件，创建文档版本与处理任务；接口返回任务状态。
3. 异步解析正文，按内容结构分块，保留页码或章节，生成向量并建立关键词索引。
4. 全部成功后将新版本设为生效版本。更新期间旧版本继续服务；失败版本可查看原因并重试。
5. 删除文档时先标记不可查询，再异步清理原件、索引及相关缓存。引用预览同时检查删除状态。

首个开发闭环可以先支持 Markdown 或纯文本，便于定位检索和权限问题；试点上线前必须覆盖样本文档中确定的主要格式。

## 问答流程

1. 校验员工身份和会话所有权，计算本次允许查询的知识库。
2. 对知识库问题由后端先执行一次检索。多轮追问可结合经过权限校验的会话上下文形成检索问题。
3. 合并关键词与向量检索结果，去重、排序，并限制片段数量和上下文长度。
4. 将带引用编号的片段作为资料交给 Pi。资料不能改变系统规则或授权范围。
5. 将 Pi 的文本增量事件转换为网页事件流。引用编号由后端映射到真实文档，校验模型输出的引用编号。
6. 保存回答、来源和模型用量。无有效资料时说明未找到依据；检索故障作为故障返回，不伪装成无资料或正常回答。

首版先完成固定的检索与回答流程。复杂问题的多轮自主补查，可随后通过 `AgentTool` 注册 `knowledge_search`、`knowledge_read`；工具仍调用同一套鉴权后的检索服务。

员工问答实例只注册必要的知识库工具。每个会话使用独立的 Agent 状态，同一会话的生成请求需要串行处理或明确返回忙碌状态。

## 首批 API 草案

以下是完整首版的业务 API 草案，不是 Pi 现有接口。当前已实现的接口见[模块说明](../packages/company-agent/README.md#已实现-api)。

- `POST /api/auth/login`：后端验证测试账号并建立登录会话。
- `POST /api/auth/logout`：结束当前登录会话。
- `GET /api/me`：当前员工及可用权限。
- `GET /api/knowledge-bases`：当前员工可访问的知识库。
- `POST /api/knowledge-bases`：按后台管理权限创建知识库。
- `PUT /api/knowledge-bases/:id/grants`：知识库管理员更新授权。
- `POST /api/knowledge-bases/:id/documents`：上传新文档，返回文档 ID 与入库任务 ID。
- `POST /api/documents/:id/versions`：上传文档新版本。
- `GET /api/documents/:id`：读取元数据及当前处理状态。
- `GET /api/documents/:id/source`：鉴权后访问指定生效版本或获准访问的历史版本原文。
- `DELETE /api/documents/:id`：使文档停止提供查询并安排清理。
- `POST /api/conversations`：创建当前员工的会话。
- `GET /api/conversations`：列出当前员工的会话。
- `GET /api/conversations/:id`：读取会话及当前仍可访问的历史。
- `POST /api/conversations/:id/messages`：提交问题，通过 SSE 返回检索状态、文本增量、引用和完成或错误事件。
- `POST /api/conversations/:id/runs/:runId/cancel`：取消本会话的指定生成任务。

上传、解析、问答接口应配置大小、并发、超时和重试上限；具体值在样本验证时确定。
